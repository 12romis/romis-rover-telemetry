# 0001 — Рахувати підсумки дашборду в domain з рядків одного знімка лише для читання

- **Status:** Accepted
- **Date:** 2026-10-24
- **Deciders:** 12romis (власник), Claude (design)

## Context

Сторінка показує підсумки (кількість виїздів, сума пробігу, час руху, утримання, остання напруга, останнє «отримано», прошивка, втрачені сесії) і таблицю тих самих виїздів (spec AC-01, AC-03, AC-07, AC-08). Підсумки мають збігатися з таблицею, а відсутнє значення не може стати нулем (конституція №4). Фундаментальний ADR-0003 каже «агрегації — SQL-представленнями», але тут таблиця все одно завантажує всі виїзди, тож агрегація йде по вже прочитаному набору.

## Decision drivers

- Підсумки й таблиця узгоджені: новий виїзд не може потрапити в одне і не потрапити в інше (spec AC-17, QG-3).
- «`NULL` ≠ 0» гарантується в одному місці й перевіряється на фікстурах seq 26 і 27 без Docker (конституція №4, №15; spec §6 «Коректність відсутніх значень»).
- Дедлайн 2026-10-26 і один розробник: менше рухомих частин, без нової міграції з rollback і `GRANT` (spec §1).
- Права `viewer` лише на читання, транзакція має бути `READ ONLY` (конституція №10, №11).

## Considered options

1. **Чисті функції `domain` рахують підсумки з рядків, прочитаних одним знімком (`REPEATABLE READ`, `READ ONLY`)** — `db` читає виїзди (без сирих байтів) і номери з `session_gaps` в одній транзакції; `domain.dashboard` будує підсумки й хронологію.
2. **SQL-представлення з агрегатами (нова міграція `0005`)** — одно-рядкове представлення з `SUM`/`COUNT`, список виїздів окремим запитом; знімок потрібен і тут, щоб числа збігалися.

## Decision outcome

**Chosen:** варіант 1. Підсумки й таблиця будуються з одного набору рядків, тому узгоджені за побудовою; правило «сума лише за відомими значеннями + кількість без даних» живе в `domain` як `Total(sum, missing)` і тестується швидкими юніт-тестами на реальних фікстурах. Нова міграція не потрібна: `viewer` уже має `SELECT` на `sessions` і `session_gaps`. Це уточнення, а не скасування фундаментального ADR-0003: представлення лишаються способом агрегації для даних, яких сторінка не завантажує (графіки по днях у кроках 4–8). Свідомий відступ від його букви — `web` читає саму таблицю `sessions` (виїзди з `payload`, без `raw`), а не представлення; він записаний як Decision override у SAD §1 ¶4.

## Consequences

**Positive**
- Узгодженість підсумків і таблиці гарантована одним знімком, без перевірки двох запитів один проти одного.
- Нуль виїздів, відсутній пробіг і дубль перевіряються без Docker; інтеграційний тест лише підтверджує читання.
- Немає міграції, rollback і GRANT перед презентацією.

**Negative**
- Агрегація відбувається в Python над усіма виїздами: ціна росте з кількістю (при ≤ 1000 мізерна, spec §6).
- Відступ від букви фундаментального ADR-0003: частину логіки агрегації не видно в SQL; кроки 4–8 мають вирішити, де рахувати агрегати по днях.

**Neutral**
- Перехід до SQL-представлення пізніше локальний: `domain.dashboard` залишається специфікацією правил, а `db.reading` повертає інше джерело.
