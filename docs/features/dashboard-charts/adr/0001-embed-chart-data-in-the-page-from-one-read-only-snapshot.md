# 0001 — Вбудувати дані графіків у сторінку з одного знімка читання лише для читання

- **Status:** Accepted
- **Date:** 2026-10-24
- **Deciders:** 12romis (власник), Claude (design)

## Context

Сторінка вже читає всі виїзди одним знімком (`REPEATABLE READ` + `READ ONLY`) і рахує підсумки та хронологію в `domain` (summary ADR-0001). Три нові блоки з графіками мають показувати те саме сховище: новий виїзд має з'явитися в підсумках, таблиці й на графіках одночасно (spec AC-22), а збій одного блоку не повинен ламати решту сторінки (AC-19). `docs/architecture-map.md`, написана до коду, планувала для графіків окремі JSON-ендпоінти (адреси, що віддають дані без HTML), які браузер викликає скриптом. Відкотити вибір пізніше — кілька днів роботи: змінюються маршрути, шаблони, `charts.js` і тести.

## Decision drivers

- Графіки, підсумки й таблиця не розходяться: усі беруться з одного набору рядків (spec AC-22, §6 «Актуальність»: кешування даних — 0 с).
- Незалежність блоків: 0 збоїв решти сторінки за збою одного блоку (spec §6 «Ізоляція блоків», AC-19).
- Строгий CSP `default-src 'self'` і лише читання: чим менше нових поверхонь (маршрутів, `fetch`), тим менше перевірок безпеки (spec §6.1, конституція №10–№12).
- Дедлайн 2026-10-26 і один розробник: менше рухомих частин, без стану «завантаження» й «помилка мережі» у браузері.

## Considered options

1. **Вбудувати дані в `GET /`** — `domain/charts.py` будує ряди трьох блоків з рядків того самого знімка; `web` кладе кожен блок у сторінку як `<script type="application/json">` через `|tojson`; `charts.js` лише читає й малює. Нових маршрутів немає.
2. **Три JSON-ендпоінти** (`/charts/battery`, `/charts/obstacles`, `/charts/motion`) — `charts.js` викликає їх через `fetch`; кожен ендпоінт має власний запит до БД і власний знімок.
3. **Гібрид** — дані двох перших блоків вбудовані, третій («Рух і борти», найперший кандидат на відкидання за ризиком дедлайну) підвантажується ендпоінтом.

## Decision outcome

**Chosen:** варіант 1. Підсумки, таблиця і графіки будуються з одного набору рядків, тому узгоджені за побудовою (як у summary ADR-0001); блок, що не збудувався, ловиться `try/except` на межі `web` окремо для кожного блоку й замінюється повідомленням (AC-19). Новий код не додає маршрутів, заголовків безпеки чи `fetch`; стану «завантаження» немає. Варіант 2 дає самостійне падіння блоків «з коробки», але ціною окремих знімків: графік міг би показати 5 виїздів, а підсумки — 4, що суперечить AC-22; варіант 3 подвоює механізми доставки заради блоку, який можна просто не збирати.

## Consequences

**Positive**
- Графіки, підсумки й таблиця узгоджені за побудовою; один запит до БД на сторінку, як і досі.
- Жодного нового маршруту, `fetch` чи стану «помилка мережі»; поверхня безпеки не росте.
- Правила `null` ≠ 0 перевіряються `pytest` на `domain/charts.py` без браузера.

**Negative**
- HTML росте з кількістю виїздів: дані трьох блоків додаються до вбудованих звітів таблиці (≤ 1000 виїздів за spec §6; точний розмір — замір у `plan-tests`).
- Без скрипта графіка немає: на місці блоку лишається опис і повідомлення, що графік недоступний (опис, схема датчиків і таблиця працюють).
- Дані мають екрануватися лише через `|tojson`; будь-який інший спосіб вставки зі звіту — вразливість (контролюється тестом із шкідливою фікстурою).
- Карта архітектури застаріває щодо «JSON-ендпоінтів»; позначено в SAD §1 ¶4 і §11.

**Neutral**
- Якщо пізніше знадобляться оновлення без перезавантаження або фільтри (spec §3 їх виключає), ендпоінти додаються поверх тих самих функцій `domain/charts.py`.
