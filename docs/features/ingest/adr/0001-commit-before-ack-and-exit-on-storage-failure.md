# 0001 — Підтверджувати звіт брокеру лише після COMMIT і виходити з процесу при збої сховища

- **Status:** Accepted
- **Date:** 2026-10-23
- **Deciders:** 12romis (власник), Claude (design)

## Context

Ровер після підтвердження брокера стирає звіт зі свого буфера (тримає лише 2 недоставлені), тож звіт, який `ingest` підтвердив, але не зберіг, зникає безповоротно (конституція №7, spec AC-01, AC-18). Брокер повторно віддає непідтверджене повідомлення лише після перепідключення клієнта з тим самим client id і `clean_session=false`, а не сам по собі. Рішення визначає цикл життя процесу `ingest` (SAD §5, §6, §7) і політику перезапуску в `docker-compose.yml`.

## Decision drivers

- Збереженість: 0 звітів, підтверджених брокеру без збереження (spec §6, конституція №7).
- Самовідновлення і наздоганяння: ≤ 60 с після збою, до 1000 накопичених повідомлень ≤ 60 с (spec §6).
- Callback paho працює в мережевому потоці: якщо він блокується довше за keepalive, клієнт не відповідає на ping брокера і з'єднання розривається.
- Мало коду: проєкт з одним розробником і дедлайном 2026-10-23 (SAD §2).

## Considered options

1. **Вийти з процесу і дати Docker перезапустити.** При збої запису чи COMMIT процес пише помилку в лог, відключається без підтвердження й завершується з ненульовим кодом; `restart: unless-stopped` піднімає його, брокер віддає непідтверджене знову, `ON CONFLICT DO NOTHING` гарантує «рівно один раз».
2. **Повторювати запис у процесі.** Callback блокується й повторює INSERT із наростаючою паузою, поки БД не повернеться.
3. **Окрема внутрішня черга й робочий потік.** Callback лише кладе повідомлення в чергу, потік пише в БД і підтверджує; мережевий потік не блокується.

## Decision outcome

**Chosen:** варіант 1. Повідомлення обробляються по одному в callback: розбір → INSERT → COMMIT → `ack`; з кожного повідомлення COMMIT робиться окремо (без пакетного запису). Помилка запису чи COMMIT — вихід із кодом 1 без `ack`. Щоб відновлення вкладалося в ≤ 60 с і не росла пауза між перезапусками Docker, на старті процес спершу чекає доступності БД (опитування в процесі, інтервал — параметр конфігурації, значення обирає `tasks`) і лише потім підключається до брокера та підписується. Таймаути підключення й запиту до БД — кілька секунд, менше за keepalive. Варіант 2 відхилено через блокування мережевого потоку, варіант 3 — через зайвий код і стан «напівживий» у дедлайн-фічі.

## Consequences

**Positive**
- Найменше коду: немає циклу повторів, черги й потоків; стан після кожного збою чистий.
- Відновлення спирається на постійну сесію брокера (черга до 1000 повідомлень), а не на пам'ять процесу.
- Підтвердження після COMMIT + `ON CONFLICT DO NOTHING` дають «принаймні раз» у доставці й «рівно раз» у збереженні.

**Negative**
- Якщо з'єднання з брокером розірвалося між COMMIT і `ack`, підтвердження не надсилається (id повідомлення з попереднього з'єднання недійсний), і звіт прийде як дубль — це допустимо, дубль ігнорується (AC-03).
- Пауза між перезапусками Docker наростає за політикою перезапуску Docker; без очікування БД на старті це з'їдало б увесь запас NFR «≤ 60 с».
- У логах під час простою БД видно серію перезапусків (шум, але не втрата).

**Neutral**
- Перехід на варіант 3 пізніше можливий без зміни схеми БД; змінюється лише `ingest`.
