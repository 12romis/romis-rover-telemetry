# Контекст для агента, що будує дашборд звітів ровера

## Що це за система

Ровер на ESP32-S3: танковий привід (два борти, по два колеса), керування з пульта радіоканалом, чотири далекоміри (спереду три, ззаду один), акумулятор 2S. Після кожного виїзду (сесії) ровер сам надсилає на сервер повідомлень один JSON-звіт. Це **єдине джерело даних** для дашборду. Опис полів — [events.md](../contracts/events.md).

Джерело істини по роверу: репозиторій ровера (`docs/features/phase8-session-report/` — spec, SAD, ADR, `contracts/events.md`). Цей файл — стислий зріз для споживача.

## Які питання має закривати дашборд

Користувач — один власник ровера. Він хоче бачити історію виїздів без підключення кабелем:

- як зростають пробіг і час руху; скільки виїздів, яка тривалість;
- стан акумулятора: напруга на старті, наприкінці, мінімум (просадка), тренд між виїздами;
- чому закінчився виїзд (роззброєння, втрата зв'язку, низька напруга);
- скільки разів ровер зупинявся перед перешкодою, який датчик і з якої відстані; скільки часу був вимкнений захист;
- чи один борт повільніший за інший (дисбаланс), швидкості бортів;
- яка версія прошивки була на виїзді;
- чи нема втрачених сесій (пропуски `seq`).

## Що важливо знати про дані

- **Дедублікація:** унікальний ключ (`mac`, `seq`). Доставка «принаймні раз», дублікати нормальні. Пропуск у `seq` = втрачена сесія.
- **Часу події немає:** на ровері немає годинника. Використовуйте час отримання на сервері й не видавайте його за час сесії. Додавання часу в подію заплановане (див. events.md) і ще не реалізоване.
- **Відсутні дані — `null`**, не нуль. Нуль — виміряне значення. Борт без енкодера, відсутня напруга, сесія без утримань дають `null` у відповідних полях.
- Звіти надходять **не одразу і не по порядку отримання**: ровер вмикає мережу лише після роззброєння на кількадесят секунд; якщо мережі немає, тримає до двох звітів і доставляє пізніше.
- Звіт описує одну сесію цілком; під час руху нічого не надсилається. Керування ровером з сервера **неможливе й не планується** (вхідного каналу немає).
- Один власник, один-кілька роверів (розрізняє `mac`). Персональних даних немає, геопозиції немає.
- Деякі значення є **виміряними константами ровера** (діаметр колеса 44 мм, поріг перешкоди зараз 190 мм, відсічка 6.0 В). Не підставляйте інших чисел для розрахунків; якщо потрібна константа, якої немає в events.md, — спитайте власника.

## Межі відповідальності

- Дашборд лише читає й показує. Він не змінює прошивку і не припускає полів, яких немає в events.md.
- Якщо дашборду потрібне нове поле в події, це запит до власника ровера: зміна прошивки й контракту, а не обхід на стороні сервера.

## Як налаштувати ту саму методологію (SDD)

На роверному проєкті використано Spec-Driven Development: плагін `sdd` для Claude Code. Кожна стадія читає артефакт попередньої, а без нього відмовляє. Артефакти лежать у `docs/features/<slug>/`.

1. **Встановлення плагіна.** Репозиторій `https://github.com/genkovich/sdd`:
   - `/plugin marketplace add genkovich/sdd`
   - `/plugin install sdd@sdd`
   - після встановлення перезапустити Claude Code.
2. **Конституція проєкту.** Файл `docs/constitution.md` з правилами, які агент не обговорює на жодній стадії (нумеровані пункти: безпека даних, заборонені підходи, мова коментарів і комітів, вимога «без нових попереджень», заборона змінювати канонічні файли без згоди). Підключіть її в `CLAUDE.md` рядком `@docs/constitution.md`.
3. **`CLAUDE.md` проєкту.** Команди збірки й тестів, порядок роботи (одна «фіча» = один слаг у `docs/features/<slug>/`), правило «не комітити й не пушити без прямої вказівки».
4. **Налаштування:** `/sdd:config` створює `.claude/sdd.local.md`. На роверному проєкті: мова документів — українська (`artifact_language: uk`), глибина опитування `medium`, `tdd: true`.
5. **Старт проєкту:** `/sdd:survey` (порожній репозиторій — фундамент і скелет, потім `/sdd:scaffold`); `/sdd:interview` для сирої ідеї; `/sdd:roadmap` розкладає ідею на кроки зі слагами.
6. **Конвеєр однієї фічі** (кожна стадія закінчується блоком «що далі», між стадіями `/clear`):
   `/sdd:specify` → `/sdd:clarify` → `/sdd:classify-size` → `/sdd:design` → `/sdd:sequences` → `/sdd:data-model` → `/sdd:api` → `/sdd:plan-tests` → `/sdd:tasks` → `/sdd:implement` → `/sdd:review` → `/sdd:ship`.
   Для фічі з інтерфейсом (дашборд ним є) додаються `/sdd:design-system` (раз на репозиторій), `/sdd:ux-flows` і `/sdd:screens`.
7. **Правила, які варто перейняти:** жодного числа чи порога без джерела («не вигадується»); кожен критерій приймання (AC) простежується до коду й тесту; незалежне рев'ю в чистому контексті перед PR; відкриті питання записуються у spec §8 з власником і терміном.

Дашборд варто почати з `/sdd:specify` на основі цього файлу та events.md; `/sdd:interview` корисний, якщо вимоги до дашборду ще не сформовані.
